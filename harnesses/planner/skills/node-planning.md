# Planner Skill：面向学习者的实验节点规划

## 使用时机与边界

- 仅在 ConfirmedIntent 已确认后、创建实验树时调用一次；只规划，不追问学生，也不在学生执行期间自动重规划。
- 只依据确认的目标、可观察成果、学生基础、技术栈、时间和难度规划。不得把未确认的假设伪装成需求。
- 输出必须符合 ExperimentTree 合同：一个根节点、唯一 key、真实 parent_key、depth 与父节点一致、每个节点 3–7 个任务、总预计时间在预算内。
- 节点 key 仅可用小写字母、数字和连字符；层级由 parent_key/depth 表达。标题可用 `3`、`3.1`、`3.1.1` 这样的学习路径编号帮助阅读，但编号不能代替结构字段。

## 规划流程

1. 将最终可观察成果作为主线，识别完成成果必需的阶段、先后依赖和学生已有基础；删去不服务于成果或验收的内容。
2. 先形成粗粒度阶段，再逐个检查阶段是否足够小。只要学生无法在一个可安排的学习时段内完成并自验、交付物包含多个可独立验收成果、或任务横跨多个主要技术能力，就继续递归拆成子节点，直到每个叶节点都有单一、明确且可验证的阶段成果。
3. 用树表达真实的学习层次与依赖。例如，`3 实现核心接口` 可以细分为 `3.1 实现请求校验`，再细分为 `3.1.1 校验必填字段`、`3.1.2 校验字段格式`。子节点应缩小范围、增加可执行性；不能只是把父标题换个说法。
4. 仅当同一前置阶段之后存在彼此可独立完成的成果时创建兄弟分支。必须按统一的父节点完成规则检查分支是否会过早解锁；不要创建依赖多个兄弟分支汇合的节点，因为当前合同只支持单父节点和单一父依赖。无法安全表达的汇合流程应改成合法的顺序结构，不得伪造多前置依赖。
5. 对每个节点定义一个学习者可理解的阶段产出；父节点自身也必须有真实的 3–7 项任务和验收结果，不能只充当目录或空壳。子节点继续推进或细化产物，不重复父节点已完成的任务。
6. 将超大任务继续拆为子节点，不要把一项复杂功能的多个实现步骤塞进一个节点的长任务清单。反过来，纯机械、无独立产出的微步骤应合并为一个任务。
7. 检查整棵树的时间总和、难度递进、节点数量上限和学生完成顺序。时间不足时删减可选成果或降低范围，不得压缩到无法练习和验证的粒度。

## 任务与验收要求

- 每节点 3–7 项顺序任务。每项使用明确动作，指出要操作/产出的对象，并说明完成证据或验证方式；“学习、了解、熟悉、完成某模块”不能单独作为任务。
- 验收应能由学生或教师根据代码、测试结果、运行结果、截图或说明进行检查。优先采用与任务对应的 command/test 校验；确实需要判断时使用 manual。
- 按初学者视角给出可执行步骤、必要中间产物和适度提示；难度越高，减少脚手架但保留清晰目标和验收条件。
- 节点描述说明产出、作用、与前后阶段的关系和难度提示。不要塞入 SQL、数据库 ID、画布坐标、原始聊天记录或无关课程内容。

## 输出前自检

- 每个必要成果是否有节点，复杂阶段是否递归拆到可在单个学习时段完成？
- 是否存在标题重复但无新增学习成果、父子任务重复、空父节点、凑数分支或过细微任务？
- 每个子节点是否只依赖其父节点；分支是否都能按 all_prerequisites_completed 正确解锁？
- 每个节点是否有 3–7 个可执行且可验收任务？时间、难度和已确认意图是否一致？
- 仅返回合法 ExperimentTree JSON，不输出解释文本。
