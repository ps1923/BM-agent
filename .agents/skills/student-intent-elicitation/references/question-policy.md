# 追问策略

## 选择下一个问题

先列出会影响后续实验设计的缺口，再按以下顺序判断优先级：

1. 答案是否会改变最终交付物或成功标准。
2. 答案是否会改变技术路径、范围或节点数量。
3. 答案是否会改变脚手架和讲解程度。
4. 该信息是否已经能从界面状态或先前回答中得到。
5. 学生是否能够轻松回答；若不能，提供具体选项和“还不确定”。

通常优先澄清可观察成果，其次是学生起点、硬性约束和时间预算，最后才是偏好。实际顺序由已有信息决定。

## 提问规则

- 一轮只问一个主问题，不把目标、技术、时间和经验拼成调查表。
- 用学生正在描述的场景措辞，不使用“认知层级”“学习路径”等内部术语。
- 提供 2–4 个能实质改变方案的选项；选项不是必需时使用自由文本。
- 解释问题用途时只说一句，例如“这会决定实验是偏原理验证还是完整项目”。
- 已由「＋」界面提供的难度和周期属于明确输入，不再询问。
- 学生回答“不确定”时，给出一个推荐默认值及其影响，并允许确认。
- 连续四次澄清后仍存在非安全关键缺口时，展示当前理解和推荐默认值，让学生选择继续或补充；不要形成无休止访谈。

## 需要追问的例子

学生说：“我想学登录。”

优先问最终成果：

> 你希望这次实验最后达到哪一种结果：理解登录流程、完成账号密码登录 API，还是完成带 JWT 的前后端登录？这会决定实验范围和验收方式。

学生已经选择“一周、入门”，并说“我会 Java，想做 Spring Boot 登录 API”。

不要再问难度和周期。下一问应聚焦交付物或环境，例如是否从空项目开始、是否需要数据库，具体取决于已有上下文。

## 不应追问的例子

- 为了个性化而询问姓名、年龄或学校。
- 学生已明确要求 Spring Boot，却未经请求追问是否改用其他框架。
- 同时询问经验、时间、数据库、认证方式和部署平台。
- 在学生只需要理解概念时强迫其选择代码仓库、数据库或部署环境。
